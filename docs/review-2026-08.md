## 1. What the project gets right

Worth stating, because it constrains what the criticism is allowed to propose.

- **The requirement/rationale split works.** `[R-n]` tags with MUST/SHOULD, a decision
  index (§14), and "what would change it" clauses on the thin-evidence decisions is a
  better documentation structure than most funded projects manage. §11.3 (accumulate
  calibration data now, label it later) and §11.10 (letters are recognition-only because
  ASR cannot round-trip a bare phoneme) are both genuinely good reasoning that a naive
  build would have got wrong.
- **The precision-over-recall posture on pronunciation** (`[R-19]`, `[R-20]`) is correct
  and consistently carried into the UI copy. `t1Line()` never shows a bare score without
  a hedge, and the "the listener may be at fault, not you" line is exactly right.
- **`[R-10]`/`[R-41]` are actually honored.** No API key reaches the client; the Worker's
  auth is length-checked then timing-safe compared, and refuses everything when
  `SYNC_TOKEN` is unset. This is the failure mode most single-file projects get wrong.
- **`worker.js` exports its pure functions for testing.** The intent is visible even
  though the tests don't exist yet.

## 2. Requirements marked built that are not met

The design doc's §10 table and §3 "Built" list are more optimistic than the code. These
are not nitpicks: each is a binding `[R-n]`.

### 2.1 `[R-32]` — append-only logs. Not implemented at all.

`grade()` does `S.progress[card.id] = schedule(S.progress[card.id], q)`
(`index.html:1571`). The previous state is overwritten. There is no `review_log`
anywhere in the app, and `S.speech` (`index.html:1064`) stores only
`{k, d, id, tier, ok}` — no grade, no interval before/after, no track, no transcript, no
MDD result.

The rationale in §9 was "this makes scheduler changes safe to experiment with — any new
algorithm can be replayed against real history rather than tested blind." That capability
does not exist, and **the cost of the omission is not recoverable later**. Every day of
study run without a review log is a day that can never be replayed. This is the single
cheapest high-value fix in the repo: ~10 lines in `grade()`/`gradeSpeak()`, appending
`{d, id, q, track, ivBefore, ivAfter}` to `S.log`.

### 2.2 `[R-33]` / §11.3 — the calibration pool is not collecting.

The doc acknowledges this ("Calibration pool not built", §10 step 7), but the §14 index
row reads: *"Calibration pool accumulates before a reviewer exists — labels apply
retroactively; delay costs time-to-answer, not data."* **That row is currently false.**
Audio is discarded immediately after `/assess` returns (`finishMic`, `index.html:1041`);
the Worker stores nothing. Tier 2 has shipped and is producing unvalidated per-phoneme
feedback right now, so the interim protocol's own trigger condition ("active from the day
Tier 2 ships") has already fired and the protocol is not running.

Either start retaining pool audio, or amend §11.3 to say plainly that delay now *does*
cost data. The current state — a documented protocol nobody is executing — is the worst
of the three options, because it makes the reviewer search feel less urgent than it is.

### 2.3 `[R-21]` — grapheme↔phoneme alignment stored at generation time. Absent.

`genPrompt()` (`worker.js:119`) asks for arabic/transliteration/gloss/new_words/notes.
No `phoneme_seq`, no `grapheme_align`. Nothing stores them client-side either. This is
the doc's own named mitigation for §7.3, "the most pressing unsolved problem in Arabic
CAPT," and its absence is not noted anywhere in §10's status table.

### 2.4 `[R-12]` — pre-generated core audio cached on device. Not met, and the README
overstates it.

There are zero audio files (`audio/letters/.gitkeep`, `audio/words/.gitkeep`). Synthetic
audio is fetched live per word from Azure and cached only in a JS object for the session
(`ttsCache`, `index.html:670`); the device Web Speech fallback needs no network but
requires an installed Arabic voice, which `ttsCard()` itself warns is often absent.

So the README's claim —

> open **Progress → Audio coverage → Check recordings** once while online — that pulls
> every available audio clip onto your device. From then on the whole study loop, audio
> included, works in airplane mode.

— is mechanically true and practically vacuous: it pulls 146 nonexistent files. Today, an
offline learner on a device without an Arabic system voice has **no audio at all**, which
is the exact condition `[R-12]` was written to prevent ("Hearing a word is part of the
study loop, not an enhancement").

**Fix that resolves three requirements at once:** generate the 146 clips once from Azure
on the maintainer's account, commit them as `audio/…/*.mp3` labeled synthetic, and let
the existing human-recording override replace them one at a time. That satisfies
`[R-12]`, un-degrades the free path (`[R-45]`, see §4.5), and makes the offline claim
true — at a cost of a few MB and one afternoon.

### 2.5 `[R-28]` — retention gates advancement. The app uses exposure.

`reps(id) >= 2` is the definition of "known" in five places (`index.html:1125, 1140,
1141, 1244, 1272`). Two reps is reachable in two days (intervals 1 then 3). §8's Phase 0
criterion is "≥3 successful reps, interval ≥7 days," and `[R-28]` states outright that a
word counts as known "when it survives a long interval, not when it has been seen."

The home screen therefore reports "Letters known 28 / 28" after two days of grinding the
alphabet grid. That number also feeds `learnerProfile()`, so the generation pipeline is
told the learner knows words they saw twice — which is the mechanism by which generated
passages will be too hard. Change to `p.reps >= 3 && p.interval >= 7`; it is one
predicate.

### 2.6 §8 curriculum progression is entirely unimplemented, and §10 has no step for it.

There is no phase state in the app. `learner_profile.phase` (§9) does not exist,
`learnerProfile()` sends no phase, and `genPrompt()` therefore drops the §5.1 constraints
"use no grammar from `grammar_pending` or later" and the whole `grammar_cleared` /
`recent_failures` profile. The Roadmap tab is static brochure text (`ROADMAP`,
`index.html:595`).

This is a structural gap in the build sequence rather than an oversight: §10 has ten
numbered steps and **none of them is "phase tracking."** Following §10 to completion
still leaves §8 unbuilt. `[R-27]` (phases overlap) and `[R-15]` (level-appropriateness
grounded against learner state, never model consensus) both depend on state that is never
computed. Either add a step, or demote §8 to "descriptive, not implemented."

### 2.7 §11.1 / `[R-30]` — there is no Egyptian content, so the register decision is inert.

All 118 words are `reg:'msa'`. The string `'egy'` appears exactly once in the entire app,
in `regTag()` (`index.html:1199`). Consequences:

- The register tag on every card is a UI element with zero information content.
- Phase 1's gate ("~40 dialect items recognized by ear") is unreachable.
- §13 unknown #2 — "Does MSA/Egyptian integration reinforce or interfere? Retention
  curves across register tags will show it within months" — can never be answered, and
  §11.1's stated falsifier ("detectable by comparing retention curves across the two
  register tags — which `[R-30]` makes measurable") is not actually measurable.
- Reason 3 for choosing Egyptian ("one of only two Arabic locales Azure will assess") is
  load-bearing on nothing, since §11.1's own implementation note keeps assessment
  MSA-only.

§11.1 is written as a resolved-and-implemented decision and §3 lists "register tags"
under **Built**. It is a resolved decision with no content behind it. Say so, or add
~40 Egyptian listening items and make it real.

## 3. Correctness bugs

### 3.1 Date arithmetic mixes UTC and local. This breaks scheduling and the heatmap.

`today()` formats in **UTC**; `addDays()` parses `'YYYY-MM-DDT00:00:00'` as **local** and
formats back in UTC (`index.html:625–627`). Verified:

```
TZ=Asia/Kolkata   today()=2026-08-04   addDays(today,0)=2026-08-03   addDays(today,+1)=2026-08-04
TZ=America/Los_Angeles  today()=2026-08-04  addDays(today,0)=2026-08-04
```

East of UTC, `addDays(d, n)` returns `d + n − 1`. Effects there:

- **Every scheduled interval is one day short.** A card scheduled `+1` is due today.
- **Today never lights up the 30-day heatmap** — `viewProgress()` builds cells from
  `addDays(today(), -i)`, so cell `i=0` is yesterday. This is the grid `[R-38]`'s hard
  stop is read off.

And separately, in the Americas, the UTC-based `today()` rolls the day over at 17:00
local. A learner who studies at 6pm Monday and 9am Tuesday has both sessions credited to
"Tuesday": Monday shows blank on the heatmap and the streak does not advance. Losing a
streak day the learner earned is a punishment mechanic introduced by a bug, which
`[R-8]` forbids by intent.

Fix: one local-date helper used everywhere.

```js
function ymd(d){ return d.getFullYear()+'-'+String(d.getMonth()+1).padStart(2,'0')+'-'+String(d.getDate()).padStart(2,'0'); }
function today(){ return ymd(new Date()); }
function addDays(s,n){ var d=new Date(s+'T00:00:00'); d.setDate(d.getDate()+n); return ymd(d); }
```

Existing saved due-dates stay valid (they are compared as strings against `today()`).

### 3.2 `esc()` does not escape quotes, and is used inside HTML attributes.

`esc()` (`index.html:1190`) handles `&`, `<`, `>` only. It is interpolated into attribute
values in ~15 places, including model-controlled text:

- `data-say="'+esc(tok)+'"` — `tok` is a whitespace-split token of LLM-generated Arabic
  (`libraryDetail`, `index.html:1491`)
- `data-say-fb="'+esc(text)+'"` — `text` is `d.ar`, model-generated for user cards
  (`playBtn`, `index.html:664`)
- `value="'+esc(CFG.url||'')+'"` — user-typed (`syncCard`, `index.html:1411`)

A `"` in any of those closes the attribute. The inputs come from a network source (an
arbitrary article's text routed through a model) and from user typing, so this is not
purely theoretical. Two characters to fix:

```js
function esc(s){ return String(s).replace(/&/g,'&amp;').replace(/</g,'&lt;')
  .replace(/>/g,'&gt;').replace(/"/g,'&quot;').replace(/'/g,'&#39;'); }
```

### 3.3 `mergeStates()` is monotonic for things that must be reversible.

`mergeStates` (`index.html:830`) is correctly union/max-shaped for progress and history.
It applies the same shape to state that the learner must be able to *undo*:

| Field | Merge rule | Consequence |
|---|---|---|
| `settings` | `Object.assign({}, a, b)` — **remote always wins** | Toggle a setting locally; the next `syncNow()` (which runs on app open and after every session) restores the other device's value and pushes it back. Local preference changes silently revert. |
| `pinFull` | union of truthy keys | **Unpinning a word is impossible** once synced. `[R-36]`'s pin becomes one-way. |
| `userCards` | `unionById` keeps the **first** occurrence | Opting a Library word into reviews on device B never reaches device A; device A's `inReview:false` wins forever. |

All three need either a per-key `updatedAt`, or an explicit tombstone, or a decision that
settings are device-local and simply excluded from the blob (probably the right answer
for `settings` — the diacritic stage arguably *should* be per-device).

### 3.4 The alphabet grid is an uncapped XP faucet that bypasses `[R-5]`.

`gradeOne()` (`index.html:1591`) grades a letter from the Progress → Alphabet tile, awards
6 XP, advances the streak, and has no session, no cap, and no completion screen. A
learner can tap through all 28 tiles repeatedly. `[R-5]` calls the 12-card cap "an
enforced ceiling, not a default" and `[R-6]` requires every session to end on a completion
screen. This surface honors neither. It is also how "Letters known 28/28" gets reached in
one sitting (§2.5).

Either route the alphabet tiles into a normal capped session, or make them review-only
(no grading, no XP) — which fits §11.10's framing of the alphabet as a reference surface.

### 3.5 The audio coverage probe is O(146) sequential requests with a 4 s timeout each.

`probeCoverage()` (`index.html:778`) chains one `new Audio()` per file. With no clips
present and a slow or offline network, worst case is ~10 minutes of "Checking… 3 / 146."
`AUDIO_MISSING` is also never persisted, so after every reload the first tap on each word
pays a full failed-request round trip before falling back to TTS. Run 6–8 probes
concurrently and persist the miss set with a timestamp.

### 3.6 Smaller items

- `ttsCache` holds `URL.createObjectURL()` blobs that are never `revokeObjectURL`'d
  (`index.html:764`) — leaks for the session.
- `MAX_STATE_BYTES` compares `body.length` (UTF-16 units) against a byte budget
  (`worker.js:355`). Arabic-heavy state is ~2× bytes, so the real cap is roughly half of
  what's advertised. Conservative direction, but the comment is wrong.
- `expectedFor()` still has a letter-name branch (`index.html:946`) that `[R-46]` makes
  dead. Harmless now, a trap for the next person who wires a mic somewhere new.
- `ScriptProcessorNode` (`index.html:1024`) is deprecated. Fine under §11.8's
  Chromium-first policy today, but `[R-2]` commits to a multi-year horizon; AudioWorklet
  is the successor.
- `sw.js` `VERSION` is still `judhur-sw-v1` across 54 commits, despite the README's
  instruction to bump it on deploys. Nothing enforces it and nothing has broken (the
  navigation handler self-heals `index.html`), which suggests the instruction should be
  deleted rather than obeyed.

## 4. Criticism of the documentation and the choices in it

### 4.1 `[R-34]`'s amendment removed the safeguard aimed at this project's stated dominant
failure mode, and the replacement is not automated.

§11.6 names the risk plainly: "the risk is that building the system becomes the project
and Arabic never gets learned… it is mechanized." The mechanism was `[R-34]`: no step
begins until its predecessor has 14 consecutive days of use. It was retired **three days
into the first window it applied to**, by the person it constrains, citing ADHD momentum —
an argument drawn from the same §2.4 research that motivated the constraint. Whether or
not the call was right, the doc should not present it in the neutral register it uses now
("only the enforcement mechanism moved"). The enforcement mechanism *was* the requirement;
the intent without it is an intention, which §11.6's own heading rejects ("Three
conditions, not intentions").

The commit history is consistent with the risk: 54 commits in 9 days, 14 of them on a
single day, against zero recorded study sessions in the repo.

`[R-38]` is now the sole safeguard, and it is **not automated**. Nothing computes active
days; the doc claims "all three are checkable from data the app already tracks," which is
true and not the same as *checked*. The heatmap is 30 dots the owner must count by eye —
and per §3.1 the grid is off by one east of UTC. Restoring the safeguard is roughly five
lines:

```js
var active = last30.filter(function(d){ return S.history.indexOf(d)>-1; }).length;
// render "18 / 30 active days" beside the heatmap; below 15, a visible banner:
// "[R-38]: building stops until this recovers."
```

That is the highest-leverage documentation-to-code change available, because it is the
only requirement whose whole purpose is to fire when the owner is least inclined to
check it.

### 4.2 The doc is rigorous about measuring pronunciation trust and unrigorous about
measuring generation trust — and generation is the one that writes to permanent state.

§11.3 designs a careful blind, two-sided, duplicate-seeded labeling protocol before a
single pronunciation verdict is trusted. Good. Now compare generated content:

- Step 10 (cross-vendor verification, `[R-16]`; dictionary grounding, `[R-18]`) is gated
  on "do only if measured error rates warrant."
- **Nothing measures generation error rates.** No correction log, no flagged-word
  mechanism, no `[HUMAN]` review pass in §12 (which covers only pronunciation labeling and
  teaching), and §13's unknowns don't include "is the generated Arabic correct?"

So Step 10's trigger condition cannot fire, ever. Meanwhile `materialize()` writes
model-generated words with model-asserted roots straight into `S.userCards`, and one tap
promotes them into the spaced-repetition deck, where the system's entire purpose is to
drill them into permanent memory. §11.3's own warning — "a learner acting on unverified
feedback can drill an error into permanence" — applies with more force here than to
pronunciation, because pronunciation feedback is transient and a wrong diacritic on a card
is not.

Two concrete asks: (a) add a "this looks wrong" affordance on Library words that logs the
item, giving Step 10 a trigger that can actually fire; (b) add generated-content accuracy
to §13 as unknown #5, and to §12 as a `[HUMAN]` job — the same reviewer can spot-check
20 generated words a month at no extra cost.

Also note `[R-16]` and `[R-18]` are currently *violated in spirit* rather than merely
unbuilt: the root string in each generated word comes from the same model that generated
the word, and it is displayed to the learner as fact ("· root ك ت ب") with no marker
distinguishing it from the hand-curated roots. §6.5 says root correctness MUST come from a
dictionary. Until it does, generated roots should be visually marked as unverified.

### 4.3 §7.5's TTS comparison table is now decorative.

The table evaluates ElevenLabs, Habibi, ArTST, and MMS-TTS-Ara. The build uses
**Azure `ar-SA-HamedNeural`**, which appears in none of them. The actual decision — Azure,
because §11.9 prefers reusing an account the learner already needs for Tier 2 over adding
a vendor — is sound and is nowhere recorded in §7.5. A reader comparing the table to the
code concludes the table was ignored; in fact it was superseded by a good argument in a
different section. Fold the decision into §7.5 and mark the four options as "considered,
not adopted."

§7.5.1 is otherwise a model of what a design doc should do — recording the four things
that were tried and failed so nobody re-attempts them is worth more than most of the
research sections.

One caveat on its finding: "byte-identical audio for diacritized and undiacritized input"
supports "this voice ignores the harakat you supply," but not the stronger reading that it
ignores vowel information — Azure very likely runs its own diacritizer upstream and
converged on the same result for these words. That distinction matters if you ever feed it
a genuinely ambiguous form, where its guess and your stored diacritics may disagree
silently. Worth one sentence.

### 4.4 §2's sources are domains, not citations — so the claims cannot be re-checked.

§2 opens with "Sources are named so claims can be re-checked." What follows is
`abblino.com; en.wikipedia.org distributed practice; lifeskillsadvocate.com; tiimoapp.com;
adhdcentre.co.uk` — bare hostnames, no titles, no URLs, no dates. Re-checking is not
possible from that.

More substantively: **§2.4 carries the heaviest requirements in the document** — `[R-5]`
through `[R-9]`, the hard session cap, the no-punishment rule, the always-visible counters
— and its sources are ADHD-coaching vendors and a Wikipedia page. §2.3 gets an explicit
"Evidence quality" caveat warning that vendor blogs cite unnamed studies; §2.4 gets none,
despite a weaker source base. Apply the same caveat, or replace the sources: distributed
practice and immediate feedback both have real literature behind them (Cepeda et al. 2006
on spacing, for one), and citing it costs nothing.

**The 12 is unsourced.** Nothing in §2.4 produces the number 12. It is presented as
`[R-5]`, MUST, "an enforced ceiling, not a default." A magic number promoted to a binding
requirement is fine as a starting guess, but the doc should say it is a guess and name
what would revise it — and as §2.1 notes, the review log that would let you revise it
doesn't exist.

### 4.5 "Free-first" (§11.9, `[R-45]`) is in tension with the audio situation.

`[R-45]` requires the free path to stay "functional, not a degraded stub." Today, with
zero human recordings, the audio a learner gets is:

- **Paid path (Azure):** a neural Arabic voice.
- **Free path:** whatever Arabic voice the OS happens to have — and `ttsCard()` itself
  says "No Arabic voice was found on this device, so words may sound wrong (a non-Arabic
  voice reading Arabic)," while the status line for the free path reads "Set up Azure for
  markedly clearer audio."

For an app whose §2.2 identifies guttural consonants as the central difficulty, a
non-Arabic voice reading Arabic is worse than a degraded stub — it is actively
mis-teaching. The §2.4 recommendation in this review's §2.4 (commit pre-generated clips)
fixes it: the free path then gets the same audio the paid path does, and Azure's
remaining value is limited to Tier 2 assessment, which is honestly an upgrade.

### 4.6 The positionally-inferred phoneme labels are a trust risk that the doc's own
posture argues against.

`parseAzureAssessment()` ("Option B", `worker.js:200`) names flagged sounds by mapping
Azure's phoneme segments onto the reference word's letter skeleton when the counts match.
Count equality does not imply correct alignment — shadda, hamza carriers, long vowels and
assimilation can all produce a matching count with a shifted mapping. When it shifts, the
learner is told to work on the wrong sound, and `coachPrompt()` then feeds that wrong
sound to an LLM which fluently explains how to produce it.

This is precisely the trust-destroying failure `[R-19]`/`[R-20]` are built around, and it
is unvalidated because §2.2's calibration pool isn't collecting. §7.3's own conclusion is
that the phoneme-to-character mapping is unsolved; Option B solves it by assumption. Until
there are labeled items, either mark these labels as inferred in the UI or fall back to
the word-level score and skip the coaching — the doc's stated posture is that a missed
error is recoverable and a false flag is not.

Related: the two thresholds (`MDD_FLAG_THRESHOLD = 40` server-side, `>=70` / `<30`
client-side in `t1Line`) are undocumented magic numbers living in two files. They're the
knobs `[R-19]` is about; they belong in one place with a comment saying what evidence
would move them.

### 4.7 Card IDs are index-based, and the doc's own data model says they shouldn't be.

`DECK` builds `v-<rootIdx>-<wordIdx>` (`index.html:616`) with the comment "the first 10
families and their original word order are LOAD-BEARING for saved progress. Append only;
never reorder." Meanwhile `content/roots-words.json` already carries stable ids
(`r-ktb`, `w-ktb-1`) and §9's data model specifies `roots.id` as a first-class key.

The authoring source has the right design and the running app has the wrong one. Content
ordering is now permanently frozen by learner state — you cannot regroup a family, fix a
misassigned root, or sort anything, forever. This is cheap to fix *now* with a one-time
remap in the state migration and expensive to fix after more history accumulates. It also
directly contradicts `[R-3]` ("Roots MUST be a first-class entity in the data model, not
a tag on a word") — in the app a root is an array index.

### 4.8 The build sequence has no step for the thing §11.6 says is the whole point.

§10 sequences ten engineering steps. None of them is "use the app." §11.6's three
conditions are the only counterweight, and §4.1 covers what happened to two of them.
Consider adding a non-engineering row to §10's table — "Step 0, recurring: 15 study days
in the last 30" — so that the table a reader treats as the work list contains the work
that matters.

build time. As long as "authoring source" is aspirational, the JSON files are a liability:
someone will edit them believing it changes the app.

## 6. Two things not covered by any requirement

**No LICENSE file.** §11.7's entire sharing model is "fork this repo and deploy your own,"
and `backend/SETUP.md` points classmates at a one-click deploy of
`patricktsullivan/judhur`. With no license, that is all-rights-reserved by default and the
classmates have no right to the copies they were invited to make. One file, MIT or
CC-BY-SA for the content, resolves it.

**Google Fonts is a third-party runtime dependency in an offline-first app.**
`index.html:15–17` preconnects to and loads from `fonts.googleapis.com` /
`fonts.gstatic.com`, including the Arabic face (`Noto Naskh Arabic`). The service worker
caches them opaquely after first load, so it works — but:

- `[R-11]` ("the study loop MUST function with no network") is met only after a
  successful online load; a cold first run offline, or a `file://` copy, renders Arabic in

- Settings says "Nothing here leaves your device except sync, which talks only to your own

- The home screen's own hedge — "Everything runs offline **after the fonts load**" — is a
  caveat that self-hosting removes entirely.

Subsetted `woff2` for the three families is on the order of 150 KB committed once.
